# AI文档识别平台：识别阶段审计报告

日期：2026-07-01

## 目标定位

当前项目处于“识别验证台”阶段，核心目标是验证：

- OCR 对合同、银行材料、扫描 PDF 的基础识别能力；
- AI/VLM 对命中页面的核对、字段理解和复核提示能力；
- OCR 与 AI 结果不一致时，能否及时提示人工复核。

如果未来要扩展为“AI 读取合同并自动生成对应材料”的平台，识别阶段需要从“可读、可看、可验证”升级到“结构化、可追溯、可校验、可复核”。

## 接近方向的开源项目

### MinerU

项目/论文：<https://github.com/opendatalab/MinerU>，<https://arxiv.org/abs/2409.18839>

定位：高精度文档内容提取，覆盖 PDF 文本、表格、公式、图片等元素，强调预处理和后处理规则。

值得参考：

- 不只做 OCR，而是做“文档解析”：文本、表格、图片、公式、版式都进入统一解析流程。
- 强调后处理规则，说明单靠模型输出不够，必须有规则修正和结构化整理。
- 适合作为后续“复杂 PDF 解析层”的候选方案或对比基线。

对本项目的启发：

- 当前只用 RapidOCR 原始行结果，缺少 layout/table 层。
- 后续合同清单、工程量、银行流水、发票等页面，表格结构会成为瓶颈。

### Docling

项目/论文：<https://github.com/docling-project/docling>，<https://arxiv.org/abs/2501.17887>

定位：开源文档转换工具，将 PDF 等文件转为统一的富结构表示，包含布局分析和表格结构识别。

值得参考：

- “统一文档表示”比单纯 Markdown/纯文本更重要。
- 模块化架构便于扩展新的模型、格式和后续处理。
- 支持 CLI/API 的方式适合被后端流水线调用。

对本项目的启发：

- 当前 `text`、`image`、`vlm text` 分散存储，缺少统一的 `Document -> Page -> Block -> Field` 数据模型。
- 后续自动生成材料时，需要稳定的中间表示，而不是从 Markdown 再反解析。

### LayoutParser

项目/论文：<https://github.com/Layout-Parser/layout-parser>，<https://arxiv.org/abs/2103.15348>

定位：文档图像分析工具包，提供布局检测、OCR、文档处理 pipeline。

值得参考：

- 把文档页面拆成布局块，再对块做 OCR/分类/抽取。
- 适合解决“页面上哪些区域是标题、正文、表格、页眉页脚、签章”等问题。

对本项目的启发：

- 当前 OCR 记录了 `box` 和 `score`，但没有把坐标用于字段证据、高亮和复核。
- 后续应把 OCR block 坐标和 AI 字段结果关联起来。

### Unstructured

项目：<https://github.com/Unstructured-IO/unstructured>

定位：多格式文档切分与结构化元素抽取，常用于 RAG 和文档处理 pipeline。

值得参考：

- 把文档转成 typed elements，而不是一整段文本。
- 对多格式输入、分块、后续 embedding/RAG 流程有成熟设计。

对本项目的启发：

- 当前只支持 PDF，并且页面结果粒度偏粗。
- 如果后续支持合同附件、Word、图片、Excel，需要先抽象输入适配层。

### PdfTable / 表格抽取方向

项目/论文：<https://github.com/CycloneBoy/pdf_table>，<https://arxiv.org/abs/2409.05125>

定位：PDF/图片表格抽取工具，集成 OCR、布局分析、表格识别。

值得参考：

- 合同材料里“清单/工程量/金额明细/发票明细”经常是表格，不能只靠全文 OCR。
- 表格需要单元格结构、行列关系和跨页处理。

对本项目的启发：

- 当前提示词会让 AI “保留主要表格结构”，但没有程序级表格结构。
- 后续自动生成材料时，表格字段最好单独建模。

### hOCR / Tesseract 输出格式

参考：<https://en.wikipedia.org/wiki/HOCR>，<https://github.com/tesseract-ocr/tesseract>

定位：OCR 结果标准化表达，包含文本、坐标、置信度等信息。

值得参考：

- OCR 结果必须保留坐标、置信度、页面位置。
- 证据链、人工复核、高亮定位都依赖这种结构。

对本项目的启发：

- RapidOCR 的 `box/score` 已经有基础，但还没有形成标准证据结构。

## 当前项目识别阶段现状

已经具备：

- PDF 上传和页面渲染；
- RapidOCR 本地识别；
- 关键词命中页筛选；
- 页码范围筛选；
- OCR 并发、AI 并发配置；
- 手动/自动 AI 提取；
- AI 请求同时带页面图片和本页 OCR 文本；
- OCR 与 AI 不一致或不确定时提示“需要人工复核”；
- 历史任务列表和恢复；
- 页面预览、缩放、旋转、拖拽；
- 初步区分“文本识别结果”和“AI 提取结果”。

当前适合：

- 验证 OCR 和 VLM 对样本文档的能力；
- 观察哪些页面命中；
- 人工对比 OCR 和 AI 结果；
- 判断是否值得继续投入到字段抽取和自动生成材料。

当前不适合直接进入：

- 自动填写材料；
- 自动生成合同相关表单；
- 无人工复核的批量生产；
- 作为正式业务系统存储识别结果。

## 主要问题

### 1. AI 输出仍然是 Markdown 文本

目前 `AI 提取` 结果主要保存为自然语言/Markdown。虽然前端可读，但后续自动生成材料需要稳定结构：

```json
{
  "field": "合同金额",
  "value": "128000.00",
  "page": 3,
  "status": "needs_review",
  "ocr_value": "123000.00",
  "ai_value": "128000.00",
  "confidence": 0.72,
  "evidence": [
    {"page": 3, "bbox": [100, 200, 400, 240], "text": "128,000.00"}
  ],
  "reason": "OCR 与图片核对值不一致"
}
```

风险：

- 后续只能再解析 Markdown，容易不稳定。
- 字段名称、字段值、复核原因不固定。
- 很难直接进入“生成材料”流程。

建议：

- 下一轮把 AI 输出改成严格 JSON。
- Markdown 只作为调试展示，不作为主数据。

### 2. OCR 坐标和置信度没有进入主链路

当前 RapidOCR 已保存 `box` 和 `score`，但页面列表和 AI 提取没有使用这些信息。

风险：

- 无法点击字段跳转到图片位置。
- 无法高亮字段证据。
- 无法基于低置信 OCR 自动标记复核。
- 无法解释“为什么填这个值”。

建议：

- 建立 OCR block 数据结构。
- 字段结果必须关联来源 block 或 bbox。
- 前端字段表支持点击定位到来源页和区域。

### 3. 字段 schema 缺失

当前关键词只是筛页线索，AI prompt 中字段是“包括但不限于”。这适合探索，但不适合自动生成材料。

风险：

- 不同页面、不同文件输出字段名不一致。
- 缺少必填字段判断。
- 无法做类型校验。
- 无法稳定映射到目标材料模板。

建议先建立合同字段 schema：

- 字段名；
- 类型：文本、金额、日期、编号、枚举、多行表格；
- 是否必填；
- 同义关键词；
- 校验规则；
- 允许多值还是单值；
- 冲突处理策略；
- 输出模板映射。

### 4. 复核判断过于依赖模型自述

当前根据 AI 文本中的“需要人工复核、不确定、冲突”等词做判断。

风险：

- 模型可能没按格式输出。
- 模型可能该标复核但没有标。
- 程序无法精确知道哪个字段需要复核。

建议：

- 模型按字段返回 `status`。
- 程序再做格式校验和冲突校验。
- 最终复核状态由“模型判断 + 程序校验 + OCR 置信度”共同决定。

### 5. 缺少程序级校验

目前主要靠 AI 判断，程序没有系统校验金额、日期、统一社会信用代码、电话、银行卡、身份证号等。

风险：

- 数字抄错不容易被发现。
- AI 可能忽略明显格式错误。
- 自动生成材料时可能把非法值填进去。

建议：

- 金额：中文大写/小写金额一致性、千分位、币种；
- 日期：格式归一化，不判断“未来日期”，只判断格式和文件内冲突；
- 统一社会信用代码：校验位；
- 身份证号：校验位；
- 手机/电话：格式；
- 银行账号：长度和字符集。

### 6. 历史任务恢复后无法继续使用原 API Key

为了安全，历史任务不会持久化 `_api_key`。这合理，但恢复历史任务后 AI 功能会变成未配置。

建议：

- 支持服务端环境变量配置默认 API Key；
- 或支持会话级临时 Key；
- 不建议把用户 Key 明文写入任务历史。

### 7. AI 运行中状态服务重启后可能卡住

AI 队列状态保存在任务状态里。如果服务重启时某页是 `running`，恢复后可能仍显示 running，并占用并发槽。

建议：

- 服务启动时扫描历史任务，把超过阈值的 `running` 标记为 `stale_failed` 或重新入队；
- `queued/running` 应有 `started_at` 和超时策略。

### 8. 停止任务还没有覆盖 AI 队列

当前停止主要作用于 OCR。已经进入 AI 队列或运行中的页面仍可能继续执行。

建议：

- 停止任务时，把未运行的 AI queued 页面标记为 stopped；
- 已经 running 的 AI 请求无法中断时，至少完成后不要继续 dispatch 下一页。

### 9. 上传和资源边界需要加强

当前验证环境可用，但对外开放后需要限制：

- 文件大小；
- PDF 页数；
- 单页渲染像素；
- 并发任务数；
- 历史任务占用磁盘；
- 异常 PDF；
- 非 PDF 文件伪装。

建议：

- 增加上传大小限制和页数上限；
- 增加任务清理策略；
- 增加全局队列和资源限流。

## 建议的下一轮优先级

### P0：识别结果结构化

目标：把 AI 提取从 Markdown 升级为 JSON 主数据。

建议输出：

```json
{
  "page": 1,
  "fields": [
    {
      "name": "甲方名称",
      "value": "中国农业银行...",
      "status": "needs_review",
      "ocr_candidates": ["中国农业银行..."],
      "ai_value": "中国农业银行...",
      "evidence_text": "页面中出现...",
      "review_reason": "页面未明确标注甲方",
      "confidence": "medium"
    }
  ],
  "page_review_required": true
}
```

### P0：字段 schema

先做一个最小合同字段集：

- 合同编号；
- 合同名称/项目名称；
- 甲方；
- 乙方；
- 合同金额；
- 签订日期；
- 履约期限；
- 发票/付款信息；
- 签字盖章状态；
- 附件/清单页。

### P1：证据链与高亮

目标：

- OCR block 坐标进入字段结果；
- 前端字段点击后跳到来源页；
- 高亮 OCR/AI 依据位置；
- 复核时能看到 OCR 值、AI 值、图片位置。

### P1：程序校验和冲突检测

目标：

- 自动标记格式错误；
- 同字段多页多值冲突；
- OCR 与 AI 数字差异；
- 低置信 OCR；
- 必填字段缺失。

### P1：任务恢复和队列健壮性

目标：

- 服务重启后清理 stale running；
- 停止任务能停止 AI queued；
- AI 页面有超时和重试策略；
- 历史任务可继续复核。

### P2：表格和多页合并

目标：

- 合同清单、工程量、发票明细、付款计划等表格单独抽取；
- 跨页字段合并；
- 多候选值排序和复核。

## 推荐架构演进

建议逐步形成如下数据层：

```text
Job
  Document
    Page
      image
      ocr_text
      ocr_blocks[]
      layout_blocks[]
      ai_page_result
    FieldSchema[]
    FieldResult[]
      value
      normalized_value
      status
      source_page
      source_bbox
      ocr_candidates[]
      ai_value
      validation_errors[]
      review_state
```

这样后续生成材料时，流程会更稳：

```text
PDF -> OCR/布局 -> 命中页 -> AI核对式字段抽取 -> 程序校验 -> 人工复核 -> 字段确认 -> 模板填充/材料生成
```

## 结论

当前项目方向正确，已经验证了关键链路：OCR 做底稿，AI 做页面核对，人工复核差异。但它仍是“识别验证台”，不是“自动材料生成”的可靠识别底座。

下一轮最重要的不是继续美化前端，也不是盲目换模型，而是把识别结果从“可读文本”升级为“结构化字段 + 证据链 + 复核状态”。

优先顺序建议：

1. AI JSON 输出；
2. 字段 schema；
3. 字段结果表；
4. OCR bbox 证据关联；
5. 程序校验；
6. 队列和历史恢复健壮性。
