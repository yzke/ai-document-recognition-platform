Enterprise Document AI Pipeline

从 PDF 到最终业务 JSON，不依赖单次模型输出，而是用 OCR、VLM、Schema 结构约束、业务规则和人工复核组成稳定闭环。

这个系统的目标不是让大模型直接“猜出最终答案”，而是把文档识别拆成可追踪、可校验、可人工介入的工程链路。用户输入一组关键词，系统为每个关键词生成固定 JSON 模板；AI 只负责寻找候选值；规则和人工审核负责决定最终值。

最终导出的业务 JSON 只包含用户关键词对应的字段和值。OCR 坐标、证据、候选列表、置信度、路由原因都属于过程数据，用于展示、审计和人工确认，不进入默认最终 JSON。

PyMuPDF RapidOCR Qwen3-VL DeepSeek-V4-Flash JSON Schema 结构约束 业务规则引擎 人工复核
核心输入PDF 文件、页码范围、关键词模板、OCR/VLM 并发、模型配置、本机 API Key。
核心中间产物页面图片、OCR 文本与坐标、VLM 复核报告、关键词候选、Schema 结构约束结果、业务规则命中、路由状态。
核心输出默认导出纯最终 JSON；审计模式可导出页码、路由、置信度和人工状态。

根据关键词模板生成候选值，而不是直接生成最终答案。

约束

05

业务规则校验

在结构合法之后，判断候选和值是否需要人工复核。

候选/最终值硬规则校验validation + final_fields
输入

template_fields、候选列表、final_value、历史页结果。

处理

检查缺失候选、多候选、低置信、语义不匹配、金额/日期/税号/重复发票号。

产物

validation、final_fields、rule_hits、low_confidence_fields。

约束

规则校验不调用 AI。它基于候选和最终值生成结论，并决定是否升级人工。

06

置信度路由

把每页送到自动通过、人工复核或拒绝。

规则结果路由决策自动/人工/拒绝
输入

规则错误、规则警告、低置信字段、最终字段数量、人工状态。

处理

计算 routing：auto_approve、human_review、rejected。

产物

extraction_summary 和 quality_summary，供工作台顶部汇总展示。

约束

只让高置信、无规则问题的页面自动过；有歧义就人工复核。

07

人工复核

人选择候选或手动填写，最终生成固定关键词 JSON。

候选 + 证据人工确认最终 JSON
输入

候选值、OCR bbox、规则原因、VLM 报告、人工处理原因。

处理

候选默认选第一个；再次点击取消；保存后写入 final_value，通过后设置人工状态。

产物

final_fields、默认导出的最终 JSON、review_samples.jsonl。

约束

默认导出只保留关键词和值；bbox、证据、候选列表仅用于审计和人工核验。

1. 七层处理管道

01文档输入PyMuPDF

上传 PDF，解析页码范围，按 DPI 渲染每页图片，建立 job 状态和页面目录。

02OCR 提取RapidOCR

识别文字、坐标、置信度，生成全文 OCR、逐页文本和 OCR JSON。

03VLM 理解Qwen3-VL

把页面图片和 OCR 文本一起交给多模态模型，输出复核报告和差异说明。

04结构化提取DeepSeek + Schema 结构约束

根据用户关键词生成模板，AI 为每个关键词归集候选值；Schema 只校字段、类型、必填项和枚举。

05业务规则校验数据合理性校验

在结构合法之后，再检查缺失候选、多候选、低置信、语义不匹配、金额/日期等业务规则。

06置信度路由自动分流

根据规则错误、警告、低置信字段和人工状态决定自动通过、人工复核或拒绝。

07人工复核审计日志

人工选择候选或手动填写最终值，保存样本，生成固定字段最终 JSON。

设计原则：模型负责理解和候选生成，JSON Schema 负责结构稳定，业务规则负责数据合理性，人工复核负责低置信兜底。AI 不直接写入关键业务状态，最终 JSON 必须经过模板、规则和人工/自动路由。

4. 最终 JSON 是怎么生成的

核心结论：规则校验不是负责“填值”的模型步骤。AI 负责生成候选；程序可在极高置信强匹配时自动选择；人工审核可以选择候选或手动填写；业务规则负责判断这些值是否需要人工复核，并把已确认值汇总成 final_fields。

数据对象之间的关系

用户关键词
  ↓ build_template()
template_fields["发票号"]              # 固定模板字段
  ↓ LLM 只填 candidates[]
candidates[]                          # 多个候选，不是最终答案
  ↓ 自动强匹配 / 人工选择 / 手动填写
final_value                           # 单个字段的最终确认值
  ↓ validate_document()
final_fields                          # 本页最终字段字典
  ↓ ExportService.export_job()
最终业务 JSON                          # 默认导出，只保留关键词和值

三个填值来源

来源什么时候发生写入哪里说明
AI 候选结构化提取阶段template_fields[key].candidates[]AI 不应该直接拍板最终值，主要提供候选值、识别成什么字段、置信度和证据。
程序自动选择业务规则校验阶段final_value、selected_candidate_index、review_status=auto_selected只有一个候选、置信度 >= 0.9、且候选识别名和关键词语义强匹配时才自动填。
人工审核人工复核阶段final_value、manual_value、selected_candidate_index、review_status人工可以选择候选，也可以手填。候选默认选第一个；再次点击已选候选会取消，保存后留空。

6. 约束、校验与兜底

提示词约束要求模型只输出 JSON，不要 Markdown，不要额外解释；字段必须来自用户关键词模板。
JSON Schema 结构约束只校验字段名、类型、候选数组、置信度范围、source 枚举和多余字段；不判断字段值是否业务正确。
重试修复Schema 或 JSON 解析失败时，把错误作为 error hint 重新要求模型修复。
硬规则引擎对缺失候选、多候选、低置信、语义不匹配等结果做业务拦截。

Schema 结构约束片段

source: ocr | vlm | manual | unknown
confidence: number, minimum 0, maximum 1
template_fields.required: 用户输入的全部关键词
template_fields.additionalProperties: false
candidates.required: value, recognized_as, source, confidence, evidence

路由规则

状态触发条件后续动作
自动通过模板字段均有最终值，未命中错误或警告规则。可进入默认最终 JSON。
人工复核缺失候选、多候选、低置信、语义不匹配、人工未确认。进入人工审核页，选择候选或手动填写。
拒绝结构化失败、关键错误、人工拒绝。默认导出跳过；审计导出保留状态。

7. 落地设计说明

识别可靠性设计 核心思路是 OCR 和 VLM 分工，而不是二选一。OCR 负责提供精确字符串池，VLM 负责看图片版式和字段归属，后端规则和人工审核负责兜底。
JSON 稳定性设计 不要让 LLM 自己设计结构。先给完整模板，再用 JSON Schema 做运行时结构校验，失败后把错误原文反馈给同一个模型自愈重试。

OCR + VLM 分工

层优势风险系统约束
OCR数字、金额、日期、编号字符本身更稳定。排版顺序、换行、相邻关系、上下文归属可能错。只作为字符串候选池，不根据 OCR 排版推断甲乙方、金额归属。
VLM能看图片版式、表格关系、字段标签和视觉上下文。可能幻觉、漏字、把不确定字段强行填值。必须以图片版式判断字段含义，值优先从 OCR 文本中选；不确定就标人工复核。
后端规则稳定、可解释、可回放。只能校验明确规则，不能理解复杂语义。金额、日期、税号、重复发票号、候选数量、低置信度等全部过规则。
人工审核处理歧义和低置信字段。有人工成本。只把真正有歧义的单子送人工，且保存样本用于后续优化。

候选值而不是单值强提取

宽泛关键词，例如“金额”，天然可能对应支付金额、贷款金额、价税合计、不含税金额、税额。系统不要求模型猜一个唯一值，而是要求模型返回 candidates 数组，人工或规则再决定最终值。

        "recognized_as": "不含税金额",
        "evidence": "不含税金额栏"
      }
    ],
    "final_value": ""
  }
}

置信度路由

自动入库全字段置信度高、VLM 复核通过、Schema 结构合法，且业务规则校验通过。
人工审核部分字段低置信、多候选、VLM 标注需要复核、关键字段为空或语义不匹配。
拒绝/重传结构化完全失败、无可用 VLM 报告、核心字段无法解析且没有候选。

业务规则交叉校验

规则实现方式命中后处理
金额三方校验不含税金额 + 税额 ≈ 含税总额，误差超过 0.02 元报警。升级人工复核，不直接自动过。
日期格式支持 20260101、2026-01-01、2026年1月1日 等格式归一解析。解析失败进入规则错误。
税号格式15/18/20 位数字和大写字母。格式可疑进入人工复核。
同批次重复发票号同一个 job 内对已提取结果做重复检测。标记警告，进入人工确认。
页级独立路由每页独立跑 OCR、VLM、结构化、规则和路由。一页自动过不影响另一页人工复核。

8. 提示词设计

VLM 复核提示词：看图那一层

这一层的任务是图文互校，不是直接提取最终 JSON。输出故意使用自然语言报告，让视觉模型充分说明依据、差异和不确定点，后面再交给结构化提取层处理。

请作为“文档字段核对助手”处理这页扫描件。

你会同时收到：
1. 页面图片
2. 本页 OCR 文本

核对规则：
1. OCR 文本排版可能混乱，但数字、编号、日期、金额通常更准确。
2. OCR 字符串之间的先后顺序、换行、相邻关系可能完全混乱，不要根据 OCR 排版推断字段归属或逻辑关系。
3. 字段含义、位置、归属、表格关系、甲乙方关系必须以页面图片中的视觉版式和明确标签为准。
4. 请根据图片判断字段含义，再优先从 OCR 文本中选取精确字段值。
5. 如果 OCR 与图片不一致、图片不清晰、存在多个候选值，必须标记“需要人工复核”。
6. 不要猜测，不要补全不存在的信息。
7. 不要使用训练知识或知识截止时间去判断日期是否合理。

输出格式必须包含：
## 复核结论
## 字段结果
## 差异清单

VLM 动态注入

if keywords:

    prompt += "\n请优先围绕这些关键词识别相关字段、数值、日期、单位名称和页面证据。"

else:

规则 2 是核心：OCR 排版关系不可信。规则 7 用来防止模型因为训练知识或知识截止时间对 2026 年单据做幻觉判断。

Extraction Prompt：结构化提取那一层

这一层只吃文本，不看图。输入是 VLM 报告 + OCR 文本，输出是严格 JSON。视觉模型和结构化模型分开：VLM 用 Qwen3-VL，文本到 JSON 用 DeepSeek-V4-Flash。

你是文档关键词模板抽取引擎。请只输出合法 JSON，不要输出 Markdown。

用户会给出一组关键词。每个关键词都是最终 JSON 的目标字段，不能增加字段，不能删除字段。
你的任务不是自由总结文档字段，而是为每个关键词寻找候选值。

规则：
1. template_fields 的 key 必须和给定关键词完全一致。
2. 每个关键词可以有 0 到多个 candidates。
3. 如果识别到的字段名和关键词不完全一致，也可以作为候选，
   但必须在 recognized_as 中写出它在文档里实际像什么字段。
4. 如果关键词较宽泛，例如“金额”，应返回多个相关候选。
5. 不要把候选值直接当最终值，final_value 默认留空，
   除非字段名强匹配且置信度很高。
6. confidence 取 0 到 1。source 只能是 ocr、vlm、manual 或 unknown。

9. JSON Schema 结构约束与自愈重试

这里的 JSON Schema 属于结构化提取阶段的格式和结构约束层。它保证模型输出可解析、字段完整、类型正确，但不判断发票号是否真实、金额是否应该选价税合计、日期是否和行程匹配。这些属于下一层业务规则和人工复核。

为什么先给模板，不让 LLM 设计结构

最有效的格式稳定手段，是在 prompt 里直接给完整 JSON 骨架，让 LLM 只负责填 candidates，不负责设计 key。不给骨架时，模型可能把“发票号”写成 invoice_number、发票号码 或自己新增字段。

动态 Schema 构建

def build_template_schema(template_fields):
    field_names = list(template_fields.keys())
    field_schema = {
        "type": "object",
        "required": ["label", "keyword", "final_value", "review_status",
                     "selected_candidate_index", "candidates"],
        "properties": {
            "label": {"type": "string"},
            "keyword": {"type": "string"},
            "final_value": {"type": "string"},
            "review_status": {"type": "string"},
            "selected_candidate_index": {"anyOf": [{"type": "integer"}, {"type": "null"}]},
            "candidates": {
                "type": "array",
                "items": {
                    "type": "object",
                    "required": ["value", "recognized_as", "source", "confidence", "evidence"],
                    "properties": {
                        "value": {"type": "string"},
                        "recognized_as": {"type": "string"},
                        "source": {"enum": ["ocr", "vlm", "manual", "unknown"]},
                        "confidence": {"type": "number", "minimum": 0, "maximum": 1},
                        "evidence": {"type": "string"}
                    }
                }
            }
        }
    }
    return {
        "type": "object",
        "required": ["doc_type", "template_fields"],
        "properties": {
            "doc_type": {"type": "string"},
            "template_fields": {
                "type": "object",
                "required": field_names,
                "properties": {name: field_schema for name in field_names},
                "additionalProperties": False
            }
        }
    }

错误信息精确到路径

def validate_template_payload(payload, template_fields):
    schema = build_template_schema(template_fields)
    validator = Draft202012Validator(schema)
    errors = sorted(validator.iter_errors(payload), key=lambda e: list(e.path))
    return [
        (".".join(str(p) for p in e.path) or "$") + ": " + e.message
        for e in errors
    ]

自愈重试

last_error = ""
for attempt in range(3):

    try:
        parsed = extract_json_fragment(raw)
        errors = validate_schema(parsed)
        if errors:

        return parsed
    except (json.JSONDecodeError, ValueError) as exc:
        last_error = str(exc)

容错解析

def extract_json_fragment(text):
    text = text.strip()
    if text.startswith("```"):
        text = re.sub(r"^```(?:json)?\s*", "", text)
        text = re.sub(r"\s*```$", "", text)
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        pass
    start, end = text.find("{"), text.rfind("}")
    if start >= 0 and end > start:
        return json.loads(text[start:end + 1])
    raise ValueError("LLM 未返回合法 JSON")

不建议再套一层“格式校验 Agent”。把 Schema 错误直接反馈给原模型重试，通常效果接近，成本和延迟更低。

# ocr_app/validation.py
def candidate_rank(candidate, label):
    recognized = (candidate.get("recognized_as") or "").replace(" ", "")
    compact_label = str(label or "").replace(" ", "")
    semantic = 0
    if recognized and compact_label and (compact_label in recognized or recognized in compact_label):
        semantic = 0.18
    ocr_support = 0.08 if candidate.get("ocr_value") or candidate.get("bbox") else 0
    ocr_score = float(candidate.get("ocr_score") or 0) * 0.06
    return float(candidate.get("confidence") or 0) + semantic + ocr_support + ocr_score

12. API 与操作逻辑

接口作用关键行为
POST /api/jobs创建识别任务保存 job，启动 OCR 线程，按页渲染和识别。
POST /api/jobs/<job_id>/vlm批量提交 VLM校验页码范围，按 job 的 VLM 并发调度。
POST /api/jobs/<job_id>/pages/<page_no>/extract手动结构化后台提交结构化线程，避免阻塞 Flask 请求。
PATCH /api/jobs/<job_id>/pages/<page_no>/fields保存人工字段保存候选选择或手动值，重算规则和路由，写入样本。
POST /approve人工通过前端先保存字段，再设置 manual_status=approved。
GET /api/jobs/<job_id>/export导出最终 JSON默认只返回最终字段；审计模式返回全链路元信息。
