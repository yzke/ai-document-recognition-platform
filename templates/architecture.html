Enterprise Document AI Pipeline

从 PDF 到最终业务 JSON，不依赖单次模型输出，而是用 OCR、VLM、Schema、规则和人工复核组成稳定闭环。

这个系统的目标不是让大模型直接“猜出最终答案”，而是把文档识别拆成可追踪、可校验、可人工介入的工程链路。用户输入一组关键词，系统为每个关键词生成固定 JSON 模板；AI 只负责寻找候选值；规则和人工审核负责决定最终值。

最终导出的业务 JSON 只包含用户关键词对应的字段和值。OCR 坐标、证据、候选列表、置信度、路由原因都属于过程数据，用于展示、审计和人工确认，不进入默认最终 JSON。

PyMuPDF RapidOCR Qwen3-VL DeepSeek-V4-Flash JSON Schema 规则引擎 人工复核
核心输入PDF 文件、页码范围、关键词模板、OCR/VLM 并发、模型配置、本机 API Key。
核心中间产物页面图片、OCR 文本与坐标、VLM 复核报告、关键词候选、Schema 校验结果、规则命中、路由状态。
核心输出默认导出纯最终 JSON；审计模式可导出页码、路由、置信度和人工状态。

1. 七层处理管道

01文档输入PyMuPDF

上传 PDF，解析页码范围，按 DPI 渲染每页图片，建立 job 状态和页面目录。

02OCR 提取RapidOCR

识别文字、坐标、置信度，生成全文 OCR、逐页文本和 OCR JSON。

03VLM 理解Qwen3-VL

把页面图片和 OCR 文本一起交给多模态模型，输出复核报告和差异说明。

04结构化提取DeepSeek + JSON Schema

根据用户关键词生成模板，AI 为每个关键词归集候选值，不直接生成最终业务数据。

05规则校验硬规则引擎

检查缺失候选、多候选、低置信、语义不匹配、金额/日期等规则。

06置信度路由自动分流

根据规则错误、警告、低置信字段和人工状态决定自动通过、人工复核或拒绝。

07人工复核审计日志

人工选择候选或手动填写最终值，保存样本，生成固定字段最终 JSON。

设计原则：模型负责理解和候选生成，程序负责约束、校验、路由和导出。AI 不直接写入关键业务状态，最终 JSON 必须经过模板、规则和人工/自动路由。

2. 运行时数据流

用户输入
PDF、关键词、页码范围、DPI、OCR 并发、VLM 并发、模型、API Key。
任务状态
JobStore 保存 state.json，包括 page_results、vlm_results、extracted_results、quality_summary。
文件产物
pages/page_0001.png、texts/page_0001.txt、texts/page_0001.json、vlm/page_0001.json、extracted/page_0001.json。

导出结果
默认 /api/jobs/<job_id>/export 只返回最终字段 JSON；?include_review=1 返回审计包。

3. JSON 与数据契约

用户关键词模板 用户输入 10 个关键词，就生成 10 个固定字段。字段 key 不能被模型新增或删除。 
{
  "发票号": {
    "label": "发票号",
    "keyword": "发票号",
    "final_value": "",
    "review_status": "pending",
    "selected_candidate_index": null,
    "candidates": []
  }
}
最终成果 JSON 只保留关键词字段和值，不包含 bbox、证据、多个候选、置信度等过程字段。 
{
  "发票号": "031002400111",
  "金额": "2680.00",
  "日期": "2026-06-15",
  "销售方": "示例科技有限公司"
}

模板候选字段

{
  "value": "031002400111",
  "recognized_as": "发票代码",
  "source": "ocr",
  "confidence": 0.82,
  "evidence": "OCR 块命中发票代码 031002400111",
  "ocr_value": "发票代码 031002400111",
  "ocr_score": 0.91,
  "bbox": [[120, 88], [360, 88], [360, 116], [120, 116]],
  "selected": false
}

候选字段里的 bbox 是 OCR 文字块坐标，只用于页面高亮和人工核验。默认导出时会被剔除。

4. 约束、校验与兜底

提示词约束要求模型只输出 JSON，不要 Markdown，不要额外解释；字段必须来自用户关键词模板。
JSON Schema校验字段名、类型、候选数组、置信度范围、source 枚举。
重试修复Schema 或 JSON 解析失败时，把错误作为 error hint 重新要求模型修复。
硬规则引擎对缺失候选、多候选、低置信、语义不匹配等结果做业务拦截。

Schema 约束片段

source: ocr | vlm | manual | unknown
confidence: number, minimum 0, maximum 1
template_fields.required: 用户输入的全部关键词
template_fields.additionalProperties: false
candidates.required: value, recognized_as, source, confidence, evidence

路由规则

状态触发条件后续动作
自动通过模板字段均有最终值，未命中错误或警告规则。可进入默认最终 JSON。
人工复核缺失候选、多候选、低置信、语义不匹配、人工未确认。进入人工审核页，选择候选或手动填写。
拒绝结构化失败、关键错误、人工拒绝。默认导出跳过；审计导出保留状态。

5. 提示词设计

VLM 复核提示词核心

请作为“文档字段核对助手”处理这页扫描件。

你会同时收到：
1. 页面图片
2. 本页 OCR 文本

核对规则：
1. OCR 文本排版可能混乱，但数字、编号、日期、金额通常更准确。
2. OCR 文本只能作为“独立字符串候选池”使用。
3. 字段含义、位置、归属、表格关系必须以页面图片中的视觉版式和明确标签为准。
4. 如果 OCR 与图片/AI 判断不一致、图片不清晰、存在多个候选值、字段归属不确定，必须标记“需要人工复核”。
5. 不要猜测，不要补全不存在的信息。

输出格式必须包含：
## 复核结论
## 字段结果
## 差异清单

结构化提取提示词核心

你是企业文档关键词模板抽取引擎。请只输出合法 JSON，不要输出 Markdown。

用户会给出一组关键词。每个关键词都是最终 JSON 的目标字段，不能增加字段，不能删除字段。
你的任务不是自由总结文档字段，而是为每个关键词寻找候选值。

规则：
1. template_fields 的 key 必须和给定关键词完全一致。
2. 每个关键词可以有 0 到多个 candidates。
3. 如果识别到的字段名和关键词不完全一致，也可以作为候选，
   但必须在 recognized_as 中写出它在文档里实际像什么字段。
4. 如果关键词较宽泛，例如“金额”，应返回多个相关候选。
5. 不要把候选值直接当最终值，final_value 默认留空，
   除非字段名强匹配且置信度很高。
6. confidence 取 0 到 1。source 只能是 ocr、vlm、manual 或 unknown。

关键点：提示词不是唯一约束。提示词只负责第一层行为引导，后面还有 JSON Schema、后端规则、路由、人工审核和审计日志。

候选排序

# ocr_app/validation.py
def candidate_rank(candidate, label):
    recognized = (candidate.get("recognized_as") or "").replace(" ", "")
    compact_label = str(label or "").replace(" ", "")
    semantic = 0
    if recognized and compact_label and (compact_label in recognized or recognized in compact_label):
        semantic = 0.18
    ocr_support = 0.08 if candidate.get("ocr_value") or candidate.get("bbox") else 0
    ocr_score = float(candidate.get("ocr_score") or 0) * 0.06
    return float(candidate.get("confidence") or 0) + semantic + ocr_support + ocr_score

7. 人工复核与样本沉淀

人工复核页面做什么 每个关键词展示多个候选。审核员可以点击候选“定位”查看 OCR bbox 在原图上的位置，然后选择候选或手动填写最终值。
样本沉淀做什么 人工修改会写入 data/review_samples.jsonl，保存候选列表、模型值、人工最终值、OCR 文本、VLM 报告和处理原因。

样本结构

{
  "time": 1783600000.0,
  "job_id": "20260709_xxxxxxxx",
  "page_no": 1,
  "field": "发票号",
  "model_value": "031002400111",
  "manual_value": "031002400111",
  "candidates": [...],
  "reason": "人工确认发票代码可作为发票号",
  "doc_type": "发票",
  "ocr_text": "...",
  "vlm_text": "..."
}

这些样本后续可以用于 prompt 示例、规则权重调参、字段名同义词表、模型微调或回归测试。

8. API 与操作逻辑

接口作用关键行为
POST /api/jobs创建识别任务保存 job，启动 OCR 线程，按页渲染和识别。
POST /api/jobs/<job_id>/vlm批量提交 VLM校验页码范围，按 job 的 VLM 并发调度。
POST /api/jobs/<job_id>/pages/<page_no>/extract手动结构化后台提交结构化线程，避免阻塞 Flask 请求。
PATCH /api/jobs/<job_id>/pages/<page_no>/fields保存人工字段保存候选选择或手动值，重算规则和路由，写入样本。
POST /approve人工通过前端先保存字段，再设置 manual_status=approved。
GET /api/jobs/<job_id>/export导出最终 JSON默认只返回最终字段；审计模式返回全链路元信息。
